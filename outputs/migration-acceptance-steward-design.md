## Problem Statement

AI coding and migration tools can transform an application faster than a professional can verify that the transformed application still behaves correctly. Passing unit tests do not prove behavioral equivalence, authorization correctness, infrastructure safety, or operational readiness. The remaining work is repetitive but judgment-heavy: derive what must remain true, collect evidence across both versions, distinguish safe repairs from consequential changes, and decide whether to accept the migration.

Migration Proof is a Professional Agent built with Strands Agents SDK. It absorbs that verification work end to end, repairs non-consequential gaps, blocks on consequential defects, and surfaces the final decision: approve or reject the exact verified migration candidate.

## What Makes This Cool

The memorable demo begins with two versions that both pass their unit tests. The migrated version contains a subtle authorization regression that a normal green CI run misses. The Strands agent discovers the mismatch through tool-directed behavioral comparison, proves which contract changed, generates the missing regression test, and refuses to approve the cutover itself.

The human receives a decision packet tied to an immutable candidate digest. After explicit approval, the system promotes that exact candidate to the fixture's accepted release slot exactly once and returns a durable receipt. The agent supplies leverage; deterministic application code owns validation and authority.

## Target User

An application owner, engineering lead, or technical program manager responsible for accepting an AI-assisted modernization or framework migration. The initial wedge is a small web/API service migrated between framework or runtime revisions, with one clear authorization contract. The product is publicly hosted on AWS, while its MVP promotion target is the controlled fixture's accepted-release registry.

## Constraints

- The project must be newly built during the hackathon submission period.
- Strands Agents SDK must be central to planning, evidence collection, tool choice, and repair decisions.
- The project must be demonstrable end to end before September 14, 2026.
- The demo may use purpose-built source and migrated applications, but every inspection, test, repair, approval, and receipt shown must actually execute.
- No generic release-readiness scope, cross-repository knowledge graph, production incident response, or full migration engine.
- The model may propose and perform explicitly allowlisted safe repairs. It may not approve, merge, deploy to production, or authorize a cutover.
- The demo must remain understandable in under five minutes.
- A fully local, genuinely executed workflow is the guaranteed baseline. A public AWS-hosted copy is required for judging; AgentCore is a stretch enhancement only after the baseline passes.

## Premises

1. Generic code review and release testing would overlap with AWS DevOps Agent and weaken originality.
2. A useful AWS project should complement AWS Transform, Kiro, and AWS deployment tooling by solving the human acceptance bottleneck after code generation or migration.
3. A decision packet is a better primary product object than a chatbot transcript.
4. Real deterministic evidence should decide whether a candidate is acceptable; the model should decide what evidence to seek and how to explain it.
5. One meaningful human approval is more compelling than repeated confirmation dialogs.
6. A narrow, fully working migration comparison is stronger than a broad mock enterprise platform.

## Cross-Model Perspective

The independent reviewer initially preferred an AWS Marketplace launch steward because it would reduce seller friction and AWS review burden. Its deeper observation applies directly here: “Let the agent absorb coordination and uncertainty, but make the human own the commitment.” It recommended a normalized evidence graph, deterministic claim-to-proof validation, safe auto-remediation, capability-scoped approval bound to an exact package, idempotent execution, and a durable receipt.

The Marketplace concept was not selected because authentic final submission depends on seller permissions and workflow state that may be difficult to obtain within the schedule. Migration acceptance preserves the same proof-and-approval architecture while allowing the complete workflow to run in a controlled, verifiable environment.

## Approaches Considered

### Approach A: AWS Partner Launch Steward

Prepare a containerized SaaS product for AWS Marketplace by validating code, images, infrastructure, security claims, buyer documentation, and listing content. Strong AWS business value and demo narrative, but authentic end-to-end Marketplace submission presents seller-access and API risk.

### Approach B: AWS Support Case First Responder

Investigate an AWS failure, run safe diagnostics, redact evidence, test likely fixes, and file an evidence-complete support case after approval. Feasible and useful, but its investigation layer overlaps with AWS DevOps Agent.

### Approach C: Migration Proof

Compare original and AI-migrated revisions, derive an acceptance plan from a fixed check registry, run baseline and behavioral checks, generate a missing regression test, detect a semantic mismatch, and produce an approval-bound acceptance packet. Best combination of AWS relevance, originality, feasibility, and an honest end-to-end demo.

## Recommended Approach

Build Approach C as a narrow migration acceptance product, not a migration generator. The demo fixture should contain:

- an original API with tenant-scoped access;
- a migrated API that passes its unit tests but accidentally permits a cross-tenant read;
- a missing cross-tenant regression test that the agent may safely generate;
- a versioned acceptance policy selecting checks from a fixed registry, with human-readable descriptions;
- one runnable fixture service that can boot any of three immutable revisions.

The Strands agent should inspect both versions, build an acceptance plan, call bounded comparison and test tools, interpret the evidence, generate only the allowlisted regression test, rerun the failed checks, and supply an explanation and recommendation. The deterministic backend assembles the final packet and independently enforces readiness, approval, and candidate identity.

## Product Workflow

1. **Intake** — Select an original version, migrated candidate, acceptance policy, and target environment.
2. **Plan** — Strands derives the smallest evidence plan needed to evaluate the change.
3. **Inspect** — Tools inventory routes, manifests, fixture health, and tests.
4. **Compare** — The agent runs baseline tests and the tenant-boundary check against the original and candidate revisions.
5. **Repair** — The agent may generate the missing regression test under `tests/acceptance/`; its diff and rerun results remain visible.
6. **Decide** — The system produces a decision packet containing passed invariants, unresolved exceptions, evidence links, the exact candidate digest, and the recommended disposition.
7. **Authorize** — Only the human may approve the exact digest and action scope.
8. **Execute** — A deterministic backend promotes the approved candidate into the fixture's accepted release slot once.
9. **Verify** — The system confirms the resulting state and returns a durable receipt. Replays recover the same receipt.

## Strands Architecture

The Strands agent owns model-driven orchestration:

- selecting the next relevant check based on prior evidence;
- deciding whether evidence is sufficient or another tool is needed;
- classifying a detected gap as safe-to-repair or human-required;
- generating the decision packet explanation;
- stopping when policy or authority prevents further action.

Bounded tools provide:

- repository and manifest inspection;
- route and API-contract extraction;
- unit and end-to-end test execution;
- authorization-probe comparison;
- fixture startup and health verification;
- allowlisted file patching;
- evidence retrieval and packet assembly.

Deterministic backend code provides:

- tool input validation and filesystem boundaries;
- policy evaluation and pass/fail contracts;
- candidate hashing;
- approval issuance, expiry, and scope binding;
- idempotent candidate-promotion execution;
- receipt persistence and recovery.

The guaranteed development path uses a configured Strands-supported model and runs locally. A one-hour access gate determines whether an OpenAI model through Amazon Bedrock is available in the builder account and region. If it is, Bedrock becomes the submitted runtime; otherwise the supported provider used by the verified local path remains the runtime and the limitation is disclosed. AgentCore is a deployment enhancement after local end-to-end verification, not a prerequisite for product correctness.

## Five-Minute Demo

### 0:00–0:35 — The green build that is not safe

Show the original and migrated service. Both unit suites pass. State the professional problem: AI made the migration quickly, but a human still owns the production decision.

### 0:35–1:20 — Strands builds the evidence plan

Start one acceptance run. Show Strands choosing tools to inspect the candidate, run baseline tests, and compare the tenant boundary. Keep the agent trace concise and show actions in the product interface.

### 1:20–2:15 — The hidden regression

The ordinary tests remain green. A generated cross-tenant behavioral probe succeeds against the migrated service when it must fail. Show the original returning `403` and the migrated candidate returning `200`, with the exact policy invariant and evidence attached.

### 2:15–3:00 — Safe autonomous work

The agent generates the missing cross-tenant regression test, reruns it, and records the resulting evidence. It does not silently rewrite the authorization logic. That remains visible as a consequential exception requiring a separately reviewed corrected candidate.

### 3:00–3:50 — Decision packet and human authority

Show the packet: what passed, what failed, what was repaired, evidence provenance, unresolved risk, recommendation, and exact digest. Switch to the corrected candidate, rerun the focused evidence, and reach “ready for approval.” The Strands agent has no approval or merge tool.

### 3:50–4:35 — Approve and execute once

The human approves the exact corrected digest. Promote it into the fixture's accepted release slot. Show the verified target state and receipt. Replay the execution request and recover the same receipt without a duplicate action.

### 4:35–5:00 — Why it matters to AWS

Position the product as the acceptance layer after AWS Transform, Kiro, or another coding agent: faster modernization without asking humans to trust a green build blindly.

## MVP Trust Model

### Acceptance policy

The MVP policy is versioned JSON, not arbitrary prose. It contains `policy_version`, a human-readable purpose, and required check IDs selected from the fixed registry: `manifest_integrity`, `baseline_tests`, `tenant_boundary`, and `fixture_health`. Strands may choose order and supporting evidence, but it cannot add, remove, reinterpret, or waive gates.

### Candidate identity

Each run has a `run_id` and a canonical candidate manifest containing the original and candidate revision IDs; SHA-256 hashes of included application and test source, policy, lockfile, runtime configuration, agent-authored patches, and rebuilt artifact; the target environment ID; and tool versions. `.git`, SQLite files, logs, caches, bytecode, temporary files, and build outputs are excluded from the source-tree hash. Regular-file mode is normalized; symlinks are forbidden. After a safe patch, the artifact is rebuilt before its hash and final candidate digest are calculated. Canonical JSON uses sorted keys, UTF-8, normalized relative paths, and no timestamps. Approval binds the actor, run, candidate digest, target, action `promote_candidate`, and expiry. Any changed input invalidates prior evidence and approval.

### Deterministic readiness

The model plans evidence collection, but it cannot define release gates. `ready_for_approval` is true only when every policy-required check has a fresh result for the current digest, no consequential defect remains, every safe repair has been revalidated, and the fixture is healthy. Missing, contradictory, untestable, or ambiguous policy requirements fail closed.

### Corrected-candidate transition

The agent never repairs authorization or business logic. After it detects the cross-tenant regression, the run stops as blocked. Seed revisions remain immutable; every accepted patch creates a derived worktree and revision. The lineage is `faulty@A → generated-test candidate A+T (blocked) → human-corrected application B with T rebased → digest C → rerun all four gates`. The human selects corrected commit B and explicitly carries the generated regression test T forward. Evidence never carries forward, but an allowlisted patch may be rebased and must be revalidated. The system generates a new digest, invalidates all earlier evidence and approvals, and reruns every required gate.

### Safe-repair policy

The only MVP mutation is generation of one regression test under `tests/acceptance/`, capped at two files, four hunks, and 200 changed lines. The tool accepts a parsed unified diff and applies it with a library API, never a shell. Application source, authorization, infrastructure, dependency manifests, documentation, secrets, generated files, symlinks, and files outside the run workspace are forbidden. The backend rejects absolute paths, `..`, symlink escapes, binary files, and credential patterns. It records the diff, can roll back, rebuilds the candidate manifest, and reruns required checks before counting the result.

### Untrusted input and resource limits

Repository files are evidence, never instructions. Commands come from a fixed registry rather than model-authored shell. Each tool has a timeout, output-size cap, redaction pass, and run budget. Tool output is labeled untrusted before model use; secrets are redacted before persistence or display.

### Public-demo authority and isolation

Creating a run returns an unguessable run token whose hash is stored server-side; the browser receives it only in a secure, HTTP-only, same-site cookie. Viewing evidence, approving, promoting, resetting, and recovering receipts all require ownership of that run token. Every run receives an isolated fixture namespace and an independent accepted-release registry; reset operations are run-scoped and cannot touch another session. Run creation is rate-limited, inactive runs expire, and the deployment test suite exercises two concurrent judge sessions through approval and replay. The hackathon MVP deliberately avoids a full identity provider while preserving a concrete authority boundary.

## MVP Contracts

### Exact fixture invariant

Seed tenants `alpha` and `beta`, each with one private document. With an authenticated `alpha` token, `GET /documents/{beta_document_id}` must return `403` with no document fields. The original and corrected services satisfy this rule; the faulty migrated service returns `200`. A reset command deterministically recreates the same identities, ports, credentials, and data.

### Required tools

1. `inspect_candidate(run_id, version)` returns version IDs, manifest hashes, routes, and fixture health.
2. `run_baseline_tests(run_id, digest)` returns command identity, exit status, test counts, duration, and result hash.
3. `compare_tenant_boundary(run_id, original_digest, candidate_digest)` runs the exact probe against both versions and returns redacted request/response evidence plus deterministic pass/fail.
4. `apply_safe_patch(run_id, digest, patch)` enforces the allowlist, records the diff, creates a new digest, and returns the required rerun set.
5. `assemble_decision_packet(run_id, digest, agent_explanation)` reads current evidence and returns deterministic readiness plus the explanatory packet.

The first four tools are available to Strands. After the agent supplies its explanation and recommendation, deterministic backend code invokes tool 5. Approval and candidate promotion are deliberately absent from the agent tool set.

### Persistent records and evidence

SQLite stores runs, evidence metadata, approvals, executions, receipts, and the authoritative accepted candidate digest. Redacted evidence bodies and logs live in a content-addressed evidence directory on the same persistent volume; database records contain their hashes and relative paths. API evidence links resolve through those records after restart. Evidence includes run ID, candidate digest, tool name and version, timestamps, structured result, redacted log hash, and status. Approval and receipt tables enforce uniqueness for candidate digest plus action. Demo evidence is retained through judging; secrets and tokens are never stored.

The minimal decision packet contains `packet_id`, `run_id`, `candidate_digest`, `policy_version`, required check IDs, evidence IDs, repair IDs, unresolved exceptions, deterministic readiness, recommendation, and creation time. An approval contains `approval_id`, nonce, actor, run ID, candidate digest, target, action, issued/expiry times, and status. A receipt contains the idempotency key, approval ID, prior and new accepted digests, verification result, rollback outcome, timestamps, and final status.

### Run states and failure behavior

`created → planning → checking → blocked | repairable → checking → ready_for_approval → approved → promoting → verified | promotion_failed`. A corrected revision continues through `blocked → candidate_replaced → checking`; all prior evidence and approval become stale.

- The tenant probe runs three times against identically seeded fixtures. Divergent outcomes, a tool timeout, missing policy, partial fixture startup, or exhausted budget produces `blocked`, never a pass.
- On process restart, persisted state resumes; interrupted tools rerun with new evidence records. Any run left in `promoting` verifies the committed accepted digest before it can be served as verified; success finalizes the receipt, while failure transactionally restores the prior digest and records `rolled_back`.
- Concurrent promotion requests serialize on the approval record; replays return the original receipt.
- Promotion changes the authoritative accepted digest inside SQLite transactionally, then derives the displayed release-slot view and verifies the accepted digest and health.
- Failed verification rolls the pointer back and records a `rolled_back` receipt; the run ends `promotion_failed`.
- Receipt persistence is in the same SQLite transaction as the authoritative accepted digest, so no successful promotion lacks a recoverable receipt.

### Component boundary

- `fixtures/`: one service codebase exercised at original, faulty migrated, corrected migrated, and explicitly derived revisions, plus deterministic seed/reset.
- `agent/`: Strands policy, evidence-plan schema, and tool adapters.
- `core/`: manifests, policies, state machine, readiness, approvals, promotion, receipts, and redaction.
- `web/`: minimal API and workflow UI for intake, progress, packet review, approval, promotion, and receipt recovery.
- `tests/`: contract, prompt-injection, path/symlink escape, timeout, stale approval, concurrent replay, rollback, and clean-clone coverage.

## Scope Boundary

### Hackathon MVP

- One small API codebase with three immutable revisions and one tenant-boundary invariant.
- Green baseline unit suites plus the separate executed acceptance probe.
- Five evidence/repair operations, with only four exposed to the agent.
- One safe generated regression test.
- One decision-packet schema and deterministic readiness predicate.
- Digest-bound approval, local accepted-release promotion, SQLite receipt, replay recovery, and rollback test.
- Minimal workflow UI, clean-clone setup, CI, public demo, architecture diagram, and video.

### Stretch only

- AgentCore hosting; real GitHub PRs or merges; AWS Transform or Kiro integration; IAM, CloudFormation, or multi-repository inspection; generalized evidence graphs; arbitrary policy languages; and container-registry distribution.

## Distribution Plan

Ship as an open-source web application with a public GitHub repository. A local quick-start launches the product and all fixture versions through Docker Compose or one Python command. GitHub Actions runs unit, integration, security-boundary, stale-approval, rollback, and idempotency tests.

The committed public-demo baseline is one AWS-hosted container running the web/API boundary, Strands orchestration, SQLite demo state, and isolated fixture processes. It mounts one persistent volume for SQLite and redacted evidence, restores interrupted runs on restart, resets fixture data per new judge run, and exposes health and deterministic seed/reset endpoints. AgentCore replaces the orchestration hosting only if the complete baseline is green by the Day 5 gate.
